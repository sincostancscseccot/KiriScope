# KiriScope 项目计划书（架构与阶段历史）

> **当前产品方向（2026-08-10 生效）**：KiriScope 的最终表现是普通用户只选择游戏目录或 XP3、导出资源类型和新导出位置，即可开始自动解包。方案 JSON、算法和研究工具属于内部兼容层或高级研究层，不能成为普通流程的必填输入。正式验收标准见 [一键式 KiriKiri 解包器：产品契约](product/ONE_CLICK_UNPACKER.md)，下一轮工作顺序见 [一键式解包器开工清单](development/RESTART_PLAN.md)。

本文件保留早期架构设计与已完成阶段的实施记录，供追溯和复用；当它与产品契约的用户体验描述冲突时，以产品契约为准。

## 1. 项目定义

### 1.1 产品定位

KiriScope 的产品目标是一个面向 Windows 的 KiriKiri 一键式资源解包器，同时保留 GUI 与 CLI。普通用户流程只需要选择输入、资源类型和导出位置；容器解析、内容过滤/解密、艺术格式恢复、静态分析、运行时研究和结果验证都服务于这一目标。

首要价值是让用户尽可能从不同版本和定制程度的 KiriKiri 游戏中恢复可用艺术资源。研究工作台能力是将未知保护转化为下一次自动兼容项的开发路径，而不是常规用户操作。

### 1.2 合理目标

“尽量覆盖所有 KiriKiri 引擎作品”具体解释为：

1. 自动处理标准 XP3 和已经确认的内容过滤方案。
2. 对未知变体识别其失败层级并生成研究所需证据。
3. 从文件名、Adler32、偏移、分段位置、已知明文等条件搜索候选参数。
4. 从 EXE、DLL、TPF 和插件中辅助定位解密函数、常量、密钥表和调用关系。
5. 离线分析不足时，通过隔离的 x86/x64 运行时组件观察或捕获已经由游戏合法解密的资源数据。
6. 将新算法沉淀为可测试、可复用的插件或作品方案，而不是硬编码到 XP3 解析器中。

由于作品可以包含任意自定义本机代码、壳或在线依赖，项目不承诺固定版本能够自动解开每个样本。评估标准是覆盖面、诊断能力、扩展成本和结果可信度。

### 1.3 使用边界

- 目标系统：Windows 10/11，优先 x64 主程序，同时兼容分析 32 位游戏进程。
- 使用对象：个人研究者。
- 输入范围：游戏目录、EXE/DLL/TPF、XP3、单独条目、明密文对照样本及算法参数。
- 首要输出：原始条目、解密条目、通用艺术格式、验证结果和可复现报告。
- 使用前提：用户拥有样本或获得分析授权。

## 2. 功能范围

### 2.1 核心能力

- 游戏目录盘点、哈希和 KiriKiri 版本/组件识别。
- XP3 签名、索引、压缩索引、分段条目和异常结构解析。
- 文件树浏览、搜索、筛选、预览和流式批量提取。
- 内容过滤器识别、组合、参数配置、候选测试和插件加载。
- 图像、音频、视频、脚本的真实格式识别与结构验证。
- 原始、解密、转换、验证四类产物的来源追踪。
- JSON、CSV、Markdown 报告及等价 CLI 命令生成。
- 静态分析和运行时分析的证据归档。

### 2.2 艺术资源优先级

第一优先级：PNG、JPEG、BMP、TLG5、TLG6、PSB/MDF/MZS、PIMG、纹理、缩略图、分层图像和立绘差分。

第二优先级：AMV、MPG、OGG、WAV、字体和 UI 资源。

第三优先级：TJS/KAG、场景脚本、配置、存档和其他结构化数据。

### 2.3 最终逆向能力

- PE、导入表、节区、字符串、熵和插件关系初筛。
- 调用关系、算法常量、密钥表和过滤器候选识别。
- Ghidra headless 分析任务与 KiriScope 项目关联。
- 进程架构、模块、文件访问和资源加载顺序观察。
- 独立 x86/x64 研究辅助进程和受控运行时数据捕获。
- 运行时发现结果与离线实现的对照验证。
- 新方案的模板生成、测试和版本化知识库。

### 2.4 非首期范围

以下能力可以在提取与验证体系成熟后评估，不进入早期关键路径：

- XP3 重打包和游戏修改。
- 文本翻译或完整汉化编辑器。
- 自动修改 EXE、签名判断或许可证逻辑。
- 通用调试器或非 KiriKiri 引擎支持。

## 3. 成功状态模型

每个归档和条目都必须独立记录状态，禁止以单一“成功”布尔值代替：

| 等级 | 状态 | 最低证据 |
|---:|---|---|
| 0 | 未识别 | 仅有输入路径和哈希 |
| 1 | 容器已识别 | XP3 签名与基本头结构有效 |
| 2 | 索引已解析 | 索引块边界、压缩和记录结构有效 |
| 3 | 条目已定位 | 文件名、段、偏移和大小关系有效 |
| 4 | 原始数据已提取 | 所有段读取/解压完成且大小一致 |
| 5 | 内容过滤已应用 | 已记录算法、版本、参数和来源 |
| 6 | 格式结构已验证 | 魔数及格式级结构/校验通过 |
| 7 | 内容完整可用 | 图像完整解码、媒体可解析或脚本结构合理 |

报告必须保留失败发生在哪一级，以及失败前最后一项已验证事实。

## 4. 目标架构

### 4.1 技术基线

- 语言与运行时：C# / .NET 10 LTS。
- GUI：WPF，Windows 原生桌面体验。
- CLI：独立可执行程序，支持脚本化和稳定退出码。
- 核心数据：版本化 JSON 项目清单；需要高效查询时引入 SQLite。
- 大文件：异步流式读取，按场景评估内存映射，不把完整 XP3 载入内存。
- 运行时研究：主应用与 x86/x64 辅助进程隔离，使用版本化消息协议。
- 测试：xUnit、构造样本、黄金文件、损坏输入与端到端测试。

### 4.4 插件类别

- `Archive`: XP3 结构变体或外置索引。
- `ContentFilter`: 条目级加密、异或、密钥派生或字节变换。
- `ResourceDecoder`: TLG、PSB、PIMG 等格式解析与转换。
- `Analyzer`: 静态特征、候选参数或关系分析。
- `Integration`: 外部工具能力桥接。

每个插件必须声明 ID、版本、输入能力、输出能力、配置模式和安全限制。作品方案只组合算法与参数，不复制算法实现。

## 6. 开发路线图

阶段编号表示依赖关系，不强制对应公开版本号。

### 阶段 0：工程基础与证据模型

交付：解决方案骨架、构建与测试流程、项目清单格式、日志、错误模型、安全路径策略、证据状态模型。

完成门槛：GUI 与 CLI 能打开同一空项目；任务取消和错误可追踪；测试可重复执行；不会覆盖输入文件。

### 阶段 1：可靠的 XP3 读取

交付：标准 XP3 头、索引、zlib、分段记录、Adler32 元数据、文件树和原始提取。

完成门槛：构造样本与合法测试样本全部通过；能检测越界、截断、路径穿越、压缩炸弹风险和重复路径；大文件处理内存稳定。

### 阶段 2：艺术资源验证与转换

交付：格式探测、PNG 完整验证、TLG5/6、PSB 系列衔接、PIMG研究、预览和批量转换。

完成门槛：输出有来源链；损坏文件不会被标记为成功；预览与导出共享解码结果；转换失败不删除原始条目。

### 阶段 3：内容过滤器与方案库

交付：过滤器接口、流水线、CxEncryption家族、方案配置、参数候选测试、明密文差分和自动格式评分。

完成门槛：同一算法可服务多个作品方案；错误方案能被验证器拒绝；算法和参数来源进入报告；旧 9-nine 案例可作为防误报回归用例。

### 阶段 4：静态逆向辅助

交付：PE/插件关系分析、字符串和常量扫描、Ghidra headless 适配、过滤器候选报告、研究项目归档。

完成门槛：工具缺失时核心解包仍可用；外部进程命令、版本、输入哈希和输出均可追踪；分析结论区分事实与推测。

### 阶段 5：运行时研究组件

交付：进程与模块识别、文件访问观察、x86/x64辅助进程、受控捕获、离线对照和算法导出流程。

完成门槛：运行时组件默认不启用且与主进程隔离；目标选择明确；崩溃可恢复；捕获数据带来源、时点和校验信息；已发现算法能回归为离线测试。

### 阶段 6：知识库与广覆盖

交付：版本化方案库、算法指纹、兼容性矩阵、批量扫描、报告对比和插件开发模板。

完成门槛：新增作品方案通常无需修改核心代码；升级不会静默改变旧项目结论；方案具有适用版本和验证证据。

### 阶段 7：可选实用扩展

候选：XP3 重打包、松散文件覆盖测试、本地化辅助、分层素材自动合成、更丰富的脚本与媒体工具。

是否进入本阶段，应依据前六阶段的稳定性和真实使用需求单独决策。

## 7. GUI 与 CLI 规划

### 7.1 GUI 工作区

- 项目主页：样本、哈希、引擎判断和当前状态。
- 归档浏览器：树、表格、搜索、筛选和批量选择。
- 资源预览器：原始字节、格式结构、图像和元数据。
- 过滤器实验室：算法、参数、对照样本、候选评分和差异查看。
- 分析中心：EXE、插件、外部工具和运行时证据。
- 任务中心：进度、速度、取消、错误与重试。
- 报告中心：成功等级、失败分类、导出统计和复现命令。

### 7.2 CLI 命令域

预期命令结构：

```text
kiriscope scan
kiriscope xp3 list
kiriscope xp3 extract
kiriscope verify
kiriscope convert
kiriscope filter test
kiriscope analyze static
kiriscope analyze runtime
kiriscope report
```

最终参数设计以稳定、可组合、可脚本化为准。GUI 调用应用服务，不通过模拟 CLI 输出实现功能。

## 8. 测试与验证策略

- 单元测试：整数边界、块结构、路径、压缩、过滤器和格式验证器。
- 属性/模糊测试：随机及畸形 XP3 索引不得造成越界、挂死或无界分配。
- 黄金样本：由项目生成的小型 XP3，覆盖分段、压缩、重复名和过滤器组合。
- 回归样本：每个已修复问题保留最小、可合法保存的复现数据。
- 集成测试：Core、插件、CLI、GUI服务和外部工具适配。
- 端到端测试：扫描到报告的完整流程，并核对来源链和成功等级。
- 性能测试：大型归档、数万条目、并发提取、取消和低磁盘空间。

不得只用文件扩展名或八字节魔数作为完整成功依据。PNG 应验证块和完整像素解码；其他格式应建立相应的结构级与内容级验证规则。

## 9. 安全性与数据保护

- 默认以只读方式打开样本，输出必须位于显式工作目录。
- 归一化条目路径并阻止绝对路径、`..`、保留设备名和符号链接逃逸。
- 解压前检查声明大小、实际大小、比例、剩余磁盘和配置上限。
- 外部工具通过明确参数调用，不拼接未经处理的命令文本。
- 运行时研究能力必须显式开启，并清楚显示目标 PID、架构和将执行的动作。
- 日志默认不保存完整资源内容；报告记录哈希和必要片段。
- 插件视为本机代码，展示来源、版本和权限，不假设第三方插件安全。

## 10. 外部工具策略

现有 `C:\Users\25626\Reverse_Tools` 作为开发和对照环境，不复制进仓库，也不作为基本解析能力的强制依赖。

- DIE/diec：文件和 PE 初筛的可选适配器。
- Ghidra：静态分析和函数/字符串证据导出。
- GARbro：兼容性对照与已知结果比较，不作为 KiriScope 核心 XP3 实现。
- FreeMote：PSB 生态的可选桥接，并逐步明确哪些能力需要原生实现。
- ProcMon/System Informer：人工调查和证据导入，不直接捆绑。
- KrkrExtract：运行时路线的行为参考与兼容性对照，不直接依赖注入实现。

采用或链接任何第三方源代码前，单独检查许可证和再分发条件。个人使用定位不取消许可证义务。

## 11. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 作品专用算法无限多 | 无法保证自动覆盖所有游戏 | 插件化、研究工具、运行时回退和证据知识库 |
| 错误参数生成“似乎正常”的文件 | 误报解密成功 | 多级状态、结构校验、完整解码和回归样本 |
| 32/64位与不同引擎构建差异 | 运行时能力不稳定 | 独立 worker、能力探测和离线优先 |
| 巨型归档和恶意元数据 | 内存、磁盘或路径风险 | 流式处理、硬上限、预检与安全路径 |
| 第三方工具版本变化 | 适配失效 | 版本探测、松耦合和保留原始输出 |
| 研究结论过时或互相冲突 | 方案库污染 | 证据版本化、适用范围、废弃标记和回归验证 |
| 过早扩展重打包等功能 | 核心可靠性下降 | 以阶段门槛控制范围，先完成提取与验证闭环 |

## 12. 项目治理与文档纪律

- 重大技术选择写入 `docs/decisions` 的 ADR。
- 格式研究写入 `docs/formats`，算法研究写入 `docs/filters`。
- 单一游戏观察放入 `docs/research`，验证后才提升为通用结论。
- 每个缺陷必须说明影响的成功等级并尽量增加回归样本。
- 每个版本维护兼容性矩阵、已知限制和可复现构建说明。
- 任何“支持某游戏/方案”的声明必须绑定样本版本与验证范围。

### 阶段 2：PSB 预检进度

2026-08-09 已加入 M2 PSB 的保守头部预检：

### 阶段 2：BMP 验证进度

### 阶段 2：BMP 转 PNG 进度

2026-08-09 已交付首条可复现的图像转换链路：

- 解码经过结构验证的 24 位和 32 位 `BI_RGB` BMP 为顶向下 RGBA 像素数据，并设有 256 MiB 的解码大小上限。
- CLI 命令：`kiriscope convert bmp-to-png <input-bmp> <output-png>`；输出采用临时文件与无覆盖移动，不会修改输入文件。
- 内置 PNG 编码器将结果重新经 PNG 验证器核验后才写出；自动化测试覆盖行方向/BGR 转 RGBA、编码往返验证和不改动输入文件的转换流程。

### 阶段 2：WAVE 验证进度

2026-08-09 已为 RIFF/WAVE 加入保守验证：

### 阶段 2：TLG5 解码与批量转换进度

2026-08-09 已交付标准 TLG5 的首个像素解码闭环：

- 支持 3/4 通道、原始与 LZSS 压缩平面、行内差分及跨行预测，解码结果统一为顶向下 RGBA；设有 256 MiB 图像与 64 MiB 平面安全上限。
- CLI 命令：`kiriscope convert tlg5-to-png <input-tlg> <output-png>`；GUI 可预览标准 TLG5 并转换为经 PNG 验证器复核的输出。
- CLI 命令：`kiriscope convert batch-to-png <input-directory> <output-directory>` 会递归处理 BMP 与标准 TLG5，保留相对路径、跳过重解析点、拒绝输出路径冲突和写回输入树。
- TLG6、加密头和非标准变体继续保持为 `ContainerIdentified`，直至具备有样本覆盖的专用解码器；TLG5 算法来源与 MIT 许可已记录在 `THIRD_PARTY_NOTICES.md`。
- 对用户显式指定的 FreeMote `EmtConvert.exe`，`kiriscope convert tlg-to-png <input-tlg> <output-png> --freemote <tool>` 会在隔离临时目录处理输入副本、记录退出码及标准输出、复验 PNG，并以无覆盖方式移动结果；它是兼容性后备，不改变原生 TLG 结论或替代样本驱动的 TLG6 解码。

### 阶段 5：运行时研究组件完成记录

2026-08-09 已完成第一条默认关闭、可恢复的运行时研究闭环：
