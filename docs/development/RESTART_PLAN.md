# 一键式解包器开工清单

本清单将 [产品契约](../product/ONE_CLICK_UNPACKER.md) 转化为下一轮开发顺序。它只列未完成的产品工作；已完成的底层阶段记录保留在 `../PROJECT_PLAN.md`。

## 已有可复用基础

- `KiriScope.Xp3`：标准 XP3 索引读取、流式提取、压缩/分段检查和安全输出路径。
- `KiriScope.Resources`：常见资源识别、部分格式验证、TLG5/BMP 转 PNG、PSB/PIMG 原始资源探测。
- `KiriScope.Filters.BuiltIn` 与 `KiriScope.Knowledge`：方案描述、格式评分、指纹匹配与版本化知识条目。
- `KiriScope.Gui`：中文 WPF 壳、资源预览、XP3 索引浏览及显式授权的运行时证据入口。

这些组件必须继续由 GUI 与 CLI 共用；新的 GUI 不得通过模拟 CLI 文本来工作。

## 第一开工阶段：一键任务骨架

目标：让未加密/标准 XP3 及受支持完整游戏压缩包的普通用户真正走完“输入 → 类型 → 输出 → 解包”流程。

1. 新建应用服务模型：`GameInput`、`ResourceCategory`、`ExtractionPlan`、`ExtractionTaskResult` 和逐归档/逐条目进度。`GameInput` 必须明确区分游戏目录、独立 XP3 与完整游戏压缩包，并经统一的只读文件源抽象供后续流程使用。
2. 实现只读游戏目录和外层归档扫描：发现 `.xp3`、排序、上限、取消、损坏归档诊断；首个归档读取器至少覆盖 ZIP，并限制条目数、解压大小与路径；不因目录名认定游戏类型，也不把外层压缩包内容写回原位置。
3. 实现资源类别筛选：至少“全部、图片、音频、脚本、其他”，以条目路径、已提取内容签名和已知解析结果给出可解释分类。
4. 将 GUI 的默认页替换为三输入向导与任务结果页；方案 JSON 移入折叠的“高级/研究”区域。
5. 新增 CLI 等价命令，作为自动化入口而非 GUI 的实现依赖。
6. 回归：单一/多归档、完整游戏 ZIP、类别筛选、已有输出拒绝、游戏目录内输出拒绝、取消、损坏/加密/路径逃逸外层包、临时文件清理和稳定结果排序。

### 第一阶段完成门槛

对构造的标准 XP3 或完整游戏 ZIP，用户无需接触方案 JSON，即可选择“图片”或“全部”并成功导出到新目录；界面给出可打开的结果目录、导出数、跳过数和每种失败原因。外层包输入还应明确显示发现的内部归档和临时处理结果。

### 第一阶段初始实现（2026-08-10）

- `GameInput`、`ResourceCategory`、`ExtractionTaskResult` 与 `GameExtractionService` 已建立为 GUI/CLI 共用的应用服务层；输入可为游戏目录、独立 XP3 或完整游戏 ZIP。
- 目录扫描跳过重解析点并稳定排序；ZIP 作为只读虚拟目录处理，限制条目数和解压大小，拒绝路径逃逸、大小超限和重复/大小写冲突路径。包内 XP3 仅按需暂存到受管临时目录，并在任务结束或取消后清理。
- GUI 新增默认的“一键解包”页；CLI 新增 `unpack <游戏目录|XP3|游戏.zip> <新输出目录> [--category ...]`。二者都支持全部、图片、音频、脚本和其他类别，并按来源归档保留输出结构。
- 初始实现只会导出未标记加密的条目；已标记加密、损坏或不支持的条目会在任务结果中明确列为跳过/失败。自动应用受信任兼容配置仍属于第二阶段。
- 导出完成后会对受支持的资源签名执行有上限的结构验证，并在结果中分别统计已识别内容、通过结构验证、未验证和“路径类别与实际内容不一致”的条目；超出验证大小上限或没有结构验证器的格式会明确说明而不是误报失败。

## 第二开工阶段：自动兼容配置

目标：让已知加密游戏也保持三输入体验。

1. 建立受信任的内置兼容配置目录：每项绑定版本、归档/EXE 指纹、方案版本、资源类型验证和证据来源。
2. 增加确定性配置选择器：仅接受强指纹或所有必需特征均满足的匹配；并列或弱匹配必须降级为“未自动选择”。
3. 在解包计划中自动应用匹配配置，并写入报告；普通 GUI 仅显示“已识别的兼容配置”，不暴露 JSON 路径。
4. 将配置验证扩展为抽样多条目、多种目标格式和回归样本，而非单个魔数命中。
5. 用用户授权的本机样本建立第一批不入库的私有回归清单；仓库只保存合成样本、哈希和许可证允许的最小证据。

### 第二阶段完成门槛

对纳入兼容库的样本，选择游戏目录、资源类型和输出位置后可自动导出经验证的资源；报告能追溯所用配置、版本、输入指纹和验证结果。

### 第二阶段初始实现（2026-08-10）

- `KnowledgeGameCompatibilityResolver` 已接入 GUI、CLI 与一键任务服务；内置 `plugins` 目录会随 GUI/CLI 输出复制。普通 GUI 流程不会暴露 scheme JSON，CLI 的 `--knowledge-root` 仅作为高级自动化入口。
- 自动选择的门槛为：方案和兼容条目均为 `Verified`、指纹包含精确 SHA-256、所有声明条件均满足，且最终只有一个方案修订命中。报告记录方案 ID、修订版、算法、命中的输入路径/哈希、证据条件和目标范围。
- `ReferenceOnly`/`Candidate`、仅字符串或启发式指纹、缺少验证证据、加载失败和多个并列命中都不会自动应用。完整游戏 ZIP 的包内 XP3、EXE 和 DLL 会在独立安全限额内按需暂存并指纹匹配，随后立即清理；不会将整个游戏包解压到磁盘。

## 第三开工阶段：未知变体研究闭环

目标：快速把授权样本转化为可复用的一键兼容项，而不污染普通流程。

1. 将静态分析、目录扫描和知识匹配组织为“研究包”，统一关联游戏目录、XP3、EXE/插件和报告。
2. 先补足安全的离线候选验证和明密文对照；仅在确有必要且用户明确授权时评估受控动态资源捕获。
3. 为每个新增配置生成测试、证据清单、适用范围和废弃/替代关系。
4. 一旦验证通过，将配置从研究区提升至内置兼容目录，使后续用户无需 JSON 即可使用。

### 第三阶段初始实现（2026-08-10）

- 新增 `research package <游戏目录> <新报告.json>`：在不执行或修改任何游戏文件的前提下，将 XP3 的 SHA-256 与索引摘要、EXE/DLL/TPM 的静态分析、可选知识库扫描和诊断写入一个全新的 JSON 研究包。
- 研究包只记录元数据、哈希、已脱敏的静态分析结果和显式提供的既有运行时报告的哈希引用；不嵌入游戏归档、提取资源、原始二进制字符串、进程内存或运行时捕获结果。运行时采集仍须使用原有的显式授权入口。
- 报告路径必须位于游戏目录之外且尚不存在。研究包保留可复现命令，并对外部运行时报告的缺失或不可读情况记录诊断而非中断离线归档。
- GUI 的“高级研究”页提供研究包入口，并允许关联由既有显式授权流程生成的运行时报告；普通“一键解包”页仍只要求输入、资源类别与新导出目录。

## 当前不做的事

- 不把“自动猜密钥”或按游戏文件夹名称匹配当作兼容性支持。
- 不把方案 JSON、PID、Ghidra、ProcMon 或第三方工具暴露为普通解包的必填步骤。
- 不向仓库提交商业游戏、完整归档、提取资源、密钥或进程内存内容。
- 不修改游戏目录、现有 XP3、EXE 或覆盖文件。
